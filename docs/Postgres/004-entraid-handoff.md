# 004 — EntraID hand-off

**Status:** Open — items below are intentionally not solved by this Postgres migration, and are listed here so the EntraID agent picks them up cleanly.

## Why a separate phase

The auth migration (Supabase Auth → EntraID) and the database migration (Supabase Postgres → Azure Postgres) are coupled at exactly two points:

1. **`auth.users` references.** The current schema's `user_profiles.user_id` is a foreign key into Supabase's `auth.users` table. Azure Postgres has no `auth` schema. Whoever owns user identity owns this column.
2. **JWT validation.** The current code validates Supabase-issued JWTs (`supabase.auth.getUser(token)`); the future code validates EntraID-issued JWTs. Both PostgREST and the Express backend currently rely on the Supabase JWT shape.

Everything else — networking, compute, secrets, schema migration tooling, the SKU choice — is independent of identity and is done in this phase.

## Specific items the EntraID agent owns

### 1. Strip the `auth.users` FK on `user_profiles`

**File:** `backend/migrations/0000_initial.sql` (the renamed `000_one_shot_schema.sql`)

The line `references auth.users(id) on delete cascade` cannot run on Azure Postgres. The initial migration must either:

- Drop the FK and store the user identifier as a plain text/uuid column whose semantics are owned by application code, **or**
- Define a local `auth_users` table (or equivalent) and migrate the FK to that.

Recommendation: drop the FK. Store the EntraID **object ID** (`oid` claim) as a `uuid` column, indexed. Cascade behavior becomes an application concern (the user-deletion endpoint deletes profile rows; the EntraID side cannot trigger Postgres cascades anyway).

### 2. Replace the `handle_new_user()` trigger

**Current trigger:** `on_auth_user_created` on `auth.users` — auto-creates a `user_profiles` row on Supabase Auth signup. (See `0000_initial.sql` lines 42–62.)

**Replacement:** application-level. When the EntraID sign-in callback executes for the first time for a given OID, the backend `INSERT`s a `user_profiles` row. Idempotent on `(user_id)`.

### 3. Remove or rewrite the RLS policies on `user_profiles`

**Current policies:** Two `using (auth.uid() = user_id)` policies. (See `0000_initial.sql` lines 33–40.)

**Status after this phase:** RLS is no longer a security boundary because the browser does not talk to PostgREST (see `002-postgrest-and-access-pattern.md`). The policies still reference `auth.uid()`, which does not exist on Azure Postgres — the migration will fail unless we resolve them.

Recommended resolution: **remove RLS from `user_profiles` in the initial migration**, document authorization as a backend concern (`backend/src/lib/access.ts` and friends), and let the EntraID agent decide whether to reintroduce it later under a different shape (e.g. `current_setting('app.current_user_id')`).

### 4. Postgres admin authentication

**Current Bicep:** provisions Flexible Server with a SQL admin login (`mikeadmin`) and a password generated by the deploy and stored in Key Vault as `postgres-admin-password`.

**Target:** the Container App and the migration job use their **system-assigned Managed Identity** to obtain an EntraID token and authenticate to Postgres. No password exists.

Steps the EntraID agent will take:

- Set the Postgres EntraID admin to a tenant group that contains the relevant Managed Identities.
- Create database roles for the backend MI and the migration-job MI; grant minimal privileges.
- Update the connection string construction to obtain a token from `IDENTITY_ENDPOINT` and use it as the password.
- Remove `postgres-admin-password` from Key Vault.

### 5. JWT signing for PostgREST

**Current:** `PGRST_JWT_SECRET` is a shared HMAC secret in Key Vault; the backend mints service-role tokens with the same secret.

**Target:** PostgREST validates EntraID-issued JWTs via JWKS (`PGRST_JWT_SECRET` is replaced by `PGRST_JWT_SECRET_JWKS_URL`-style config, or an explicit JWKS document fetched at startup). The backend stops minting its own JWTs and instead obtains tokens via MI when calling PostgREST.

This may also lead to a re-evaluation of whether the backend needs PostgREST at all, since MI-token-then-call-PostgREST is more ceremony than calling Postgres directly. That re-evaluation is deferred until after the EntraID work is complete; today's decision (keep PostgREST) is correct under current constraints.

### 6. Replace `supabase.auth.*` calls in the frontend and backend

**Frontend (10+ callsites)** — `supabase.auth.getSession()`, `signUp()`, `signInWithPassword()`, `signOut()`, `onAuthStateChange()`. Replace with MSAL.js or `@azure/msal-browser`.

**Backend** — `frontend/src/lib/supabase-server.ts` lines 17–38 (`admin.auth.getUser(token)`). Replace with `jose`-based JWT validation against the EntraID tenant's JWKS, with audience and issuer pinning.

### 7. Data cutover plan

The actual movement of production data from Supabase Postgres to Azure Postgres is on the EntraID agent's plate because user-ID translation (Supabase `auth.users.id` → EntraID `oid`) is a prerequisite. Open questions:

- Is there a 1:1 mapping that can be derived from email + tenant, or do users re-register?
- What is the acceptable downtime window? (Big-bang `pg_dump` / `pg_restore` is operationally simplest; logical replication is more elaborate but offers a reversible cutover.)
- Are there workflows in flight (long-running document edits, in-progress chats) that need draining before cutover?

## What this phase delivers regardless

- A provisioned Azure Postgres ready to receive a schema.
- A schema migration tool wired into the deploy pipeline.
- A Bicep template parameterized to reprovision identically in any subscription.
- An empty Key Vault with the right secret slots defined.
- A backend Container App that runs against an empty database (login flow will fail, but the rest of the surface stands up).

In other words: when the EntraID agent picks this up, every infrastructure question is answered. Only the auth-coupled application changes remain.
