# Issue 008.0 — local auth provider + full-stack local dev

Spec parent: `docs/issues/azure-migration/008-backend-auth-provider-abstraction.md`

## Goal

Get the backend running end-to-end against the local Docker stack so a
desktop developer can:

- Mint a JWT
- `npm run dev` the backend with `AUTH_PROVIDER=local`
- Hit any backend route and have it read/write Postgres through PostgREST
- Have Azurite stand in for Azure Blob with no code changes

This is the **first slice of issue 008** (the part that proves the
provider switch works in anger) plus a Caddy proxy + Azurite that
complete the local-dev triangle. Entra (009) keeps its own slice.

## What already exists

- `backend/src/lib/auth/types.ts` — `AuthPrincipal`, `AuthValidationResult`.
- `backend/src/lib/auth/providers/supabase.ts` — Supabase impl.
- `backend/src/middleware/auth.ts` — switches on `AUTH_PROVIDER`,
  defaults to `supabase`, falls through to a 500 on anything else.
- `backend/src/lib/storage.ts` — already supports
  `AZURE_STORAGE_CONNECTION_STRING=UseDevelopmentStorage=true` (Azurite).
- `docker-compose.dev.yml` — Postgres + PostgREST.

## What is missing

1. A `local` auth provider that verifies HS256 JWTs against
   `JWT_SECRET` — the same secret PostgREST uses, so a single forged
   token authorises both layers.
2. Middleware wiring for the `local` branch.
3. A `service_role` Postgres role + a long-lived JWT signed for it,
   because supabase-js sends the configured `key` as both the `apikey`
   header and the `Authorization: Bearer` — PostgREST validates the
   bearer token and `SET ROLE`s into whatever the `role` claim says.
4. A Caddy proxy fronting PostgREST at `/rest/v1/*` so supabase-js
   (which prepends that prefix) hits PostgREST without code changes.
5. Azurite in compose so Blob round-trips work locally.
6. `documents` blob container created on first boot.

## Design

### Local auth provider

New file `backend/src/lib/auth/providers/local.ts`. HS256 verification
in ~30 lines using Node stdlib `crypto.timingSafeEqual` — no new
dependency. When issue 014 adds JWKS the same module gets a `jose`
upgrade and the rest of the system stays untouched.

Required claims:
- `sub` — string, becomes `principal.userId`.
- `exp` — required, rejected if past.
- `role` — optional. If present, surfaced on the principal but not
  enforced; PostgREST is the authority on what role-claim a token
  carries.

Optional claims surfaced on the principal:
- `email`, `groups[]`, `roles[]`, `tid` (→ `tenantId`).

Returns the same `AuthValidationResult` discriminated union as the
Supabase provider. Drop-in.

### Middleware

`backend/src/middleware/auth.ts` gains a `local` branch alongside
`supabase`. Anything else is still rejected.

### Postgres roles

Extend `scripts/local-stack/00-init-roles.sql` with `service_role`:
- nologin, granted to `authenticator`, granted full DML on `public`.
- Default privileges set for `mikeadmin` so future migrations
  auto-grant.

### supabase-js → PostgREST bridge

Add `caddy` service in `docker-compose.dev.yml`. Caddyfile:

```
:8000

handle_path /rest/v1/* {
    reverse_proxy postgrest:3000
}
handle_path /storage/v1/* {
    respond "storage handled by Azurite, not PostgREST" 404
}
```

Backend env becomes:

```
AUTH_PROVIDER=local
JWT_SECRET=<same as PostgREST>
SUPABASE_URL=http://localhost:8000
SUPABASE_SECRET_KEY=<service-role JWT signed with JWT_SECRET>
```

The `SUPABASE_SECRET_KEY` is just a JWT now — issued by the
`forge-jwt.mjs` helper with `--role service_role --hours 87600`
(10 years). The variable name stays so unmodified call sites work;
issues 008+ rename it later.

### Azurite

Add `azurite` service in compose using the official
`mcr.microsoft.com/azure-storage/azurite` image, ports 10000/10001/10002.
Backend env becomes:

```
AZURE_STORAGE_CONNECTION_STRING=DefaultEndpointsProtocol=http;\
AccountName=devstoreaccount1;\
AccountKey=Eby8vdM02xNOcqFlqUwJPLlmEEHlCxXulr7xzpQ4u91FhKhe2K0kjFv5dx84GjBFXzhf3lpFHJ4gT5KyDglVMA==;\
BlobEndpoint=http://localhost:10000/devstoreaccount1;
AZURE_STORAGE_CONTAINER_NAME=documents
```

The `documents` container does not exist on first Azurite boot. The
runbook documents the one-shot creation command.

## Acceptance check

- [ ] `docker compose -f docker-compose.dev.yml up -d` brings up
  postgres + postgrest + caddy + azurite. All containers healthy.
- [ ] `npm run migrate` from `backend/` applies the schema.
- [ ] `forge-jwt.mjs --role authenticated` produces a token.
- [ ] `forge-jwt.mjs --role service_role --hours 87600` produces the
  service token written into `backend/.env`.
- [ ] `npm run dev --prefix backend` boots without errors with
  `AUTH_PROVIDER=local`.
- [ ] `curl -H 'Authorization: Bearer <user-jwt>'
  http://localhost:3001/api/projects` returns the user's projects
  (200 with empty array initially, 200 with rows after a POST).
- [ ] Document upload through the backend lands in Azurite, retrievable
  via the same backend route.

## Out of scope

- Frontend integration (still uses hosted Supabase; refactored in
  013).
- Entra provider (009).
- Tenant / group enforcement (010).
- Caddy production config — local-dev only.
- Azurite container auto-creation on first start; doc the manual step
  for now.
