## OSS PR candidate — Auth provider interface

**Status: IMPLEMENTED** (this issue)

Mirrors the storage provider pattern for authentication. Introduces a provider
abstraction layer so auth behaviour can be toggled via `AUTH_PROVIDER` env var.
**Zero behaviour change when `AUTH_PROVIDER=supabase` (or unset).**

This document describes only the upstream-compatible portion. The Entra
implementation (`providers/entra.ts`) lives in the fork and is covered by issue
009.

## Parent docs

`docs/issues/azure-migration/008-backend-auth-provider-abstraction.md`

## What to build

### `backend/src/lib/auth/types.ts`

Normalized principal — no provider-specific imports:

```typescript
export interface AuthPrincipal {
  userId: string;       // Supabase: user UUID; Entra: oid claim
  email: string;
  tenantId?: string;    // provider-specific (optional)
  groups: string[];     // empty for Supabase
  roles: string[];      // empty until role mapping is added
  provider: string;     // 'supabase' | 'entra' | any future provider
}

export type AuthValidationResult =
  | { ok: true; principal: AuthPrincipal }
  | { ok: false; status: 401 | 403; detail: string };
```

### `backend/src/lib/auth/providers/supabase.ts`

Move existing validation logic from `backend/src/middleware/auth.ts` verbatim.
Export a single function:

```typescript
export async function validateSupabaseToken(token: string): Promise<AuthValidationResult>
```

### `backend/src/middleware/auth.ts`

Replace inline Supabase validation with provider dispatch:

```typescript
const provider = process.env.AUTH_PROVIDER ?? 'supabase';
// 'supabase' → validateSupabaseToken
// anything else → 500 "Auth provider not yet implemented"
```

`res.locals.userId`, `res.locals.userEmail`, `res.locals.token` remain
populated as before — all downstream route code is untouched.
`res.locals.principal` additionally set to the full `AuthPrincipal`.

## Acceptance criteria

- [ ] `AUTH_PROVIDER=supabase` (or unset): all existing protected routes behave identically.
- [ ] Unknown `AUTH_PROVIDER` value: middleware returns 500 with a clear error.
- [ ] `res.locals.userId` and `res.locals.userEmail` still set from Supabase path.
- [ ] `res.locals.principal` set on success (`groups: [], roles: [], tenantId: undefined`).
- [ ] No provider-specific imports in `auth/types.ts`.

## Why this belongs upstream

- Zero behaviour change for existing Supabase deployments.
- Allows self-hosters to plug in any identity provider (Clerk, Auth0, custom
  JWT) without touching middleware internals.
- The `AuthPrincipal` / `AuthValidationResult` types are provider-neutral.
